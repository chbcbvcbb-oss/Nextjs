V8's Defense Layers (Why Exploits Failed)

  • Deoptimization framework — JIT-compiled code deoptimizes to interpreter when type assumptions are violated. Caught all type feedback pollution attempts.
  • EnsureValidAndReadLength — Re-validates TypedArray buffer attachment after every valueOf/ToNumber call. Caught all transfer() and Wasm grow() detachment attempts in with(), slice(), fill().
  • LoadJSTypedArrayLengthAndValidate — Re-reads length from live buffer state. Used in slice(), sort() writeback, and other builtins.
  • AttachedJSTypedArrayWitness.RecheckIndex — Per-iteration re-validation for callback-based builtins (every, some, forEach, filter, map, find, reduce).
  • IncludesValueImpl defense-in-depth — Inner re-check via GetLengthOrOutOfBounds() at elements.cc:3857, catches stale length even when outer builtin misses it.
  • TypedArray.sort temp buffer — Copies data to FixedArray before sorting. Comparator-detach doesn't cause UAF.
  • RAB backing store zeroing — On resize-down, bytes between new and old length are zeroed within the same allocation (sized for maxByteLength). Prevents heap data leaks through stale-length results.
  • DataView bounds re-check — getFloat16/setFloat16 and all DataView methods re-validate offset after valueOf conversion.

Confirmed Spec Violation (Non-Security)

Spec Violation TypedArray.includes(undefined) returns true on detached buffer
builtins-typed-array.cc:247 → elements.cc:3857
When a TypedArray's buffer is detached via transfer() in the fromIndex valueOf, includes(undefined) returns true instead of throwing TypeError. The internal IncludesValueImpl at elements.cc:3863 has special handling: when the buffer is out-of-bounds and the search value is undefined, it returns true (treating OOB elements as undefined). This is a spec deviation — the spec requires TypeError for detached buffers — but it does not access freed memory and is not a security vulnerability.

Stale-Length Behavior (Spec-Compliant, Not Exploitable)

Safe TypedArray.with() and slice() return results with original (pre-resize) length
typed-array-with.tq:57 · typed-array-slice.tq:107
When an RAB is resized during valueOf, these methods create a result array using the original length (e.g., 256 elements from a now-32-byte buffer). The copy step correctly uses UintPtrMin(originalLength, currentLength), only copying valid data. Remaining elements are filled with zeros (Uint8/Uint32) or NaN (Float64/Float16). The RAB backing store is allocated for maxByteLength and zeroed on shrink, so no heap data leaks through the extra elements. This behavior is spec-compliant (the spec captures length before valueOf).

Highest-Risk Code Findings (F-34 through F-47)

Findings from automated source-level audit of Turboshaft, Maglev, and runtime code. These represent structural weaknesses that could become exploitable if combined with an undiscovered compiler bug, but none are directly triggerable from JavaScript.

High Risk F-34: Turboshaft type verification completely disabled
type-inference-reducer.h:504 — #if 0 wraps Verify()
The method that checks output_type.IsSubtypeOf(input_type) is wrapped in #if 0, meaning it never compiles in any build. If any Turboshaft reducer assigns a wrong type, the TypedOptimizationsReducer trusts it unconditionally. No runtime enforcement of type soundness exists across the Turboshaft pipeline.
High Risk F-38: Fast API call argument count — DCHECK only
fast-api-call-lowering-reducer.h:39
DCHECK_EQ(c_arg_count, arguments.size()) — in release builds, a mismatch between C signature arg count and IR argument count would cause OOB read from the arguments vector during lowering. Requires a separate compiler bug to trigger the mismatch.
High Risk F-39: ObjectIs kInternalizedString HeapObject assumption — DCHECK only
machine-lowering-reducer-inl.h:645
Loads map from input without Smi check in release. If a compiler bug omits the prior Smi guard, a Smi value would be dereferenced as a pointer address. Requires another bug to skip the Smi check insertion.
Medium F-37: Late load elimination non-aliasing validation — DEBUG only
late-load-elimination-reducer.cc:610-624
Validation that non-aliasing objects only flow into Smi-check WordBinop is #ifdef DEBUG. In release, a non-Smi-check word binop on a fresh allocation could cause stale field values to persist through load elimination.
Medium F-40: Runtime_StringReplaceNonGlobalRegExpWithFunction — DCHECK-only guards
runtime-regexp.cc:1609-1610
IsUnmodifiedRegExp and is_callable checks are DCHECK-only. The fast path for string replace trusts that callers validated these conditions. A stale dispatch could bypass these checks in release.
Medium F-41: UnsafeCast<ArrayList> in groupBy — no runtime type check
map-groupby.tq:25 · object-groupby.tq:198
Torque UnsafeCast<ArrayList> performs no type check in any build. If AddValueToKeyedGroup has a bug storing a non-ArrayList, the cast interprets arbitrary data as ArrayList fields.

Conclusion

V8 15.2.107 demonstrates mature, layered defenses against the tested exploit classes. Every callback-during-operation TOCTOU path is guarded by re-validation. JIT compilation deoptimizes correctly on type mismatches. RAB memory is zeroed on shrink. The Turboshaft pipeline has structural weaknesses (disabled verification, DCHECK-only guards) that represent future risk but are not currently triggerable from JavaScript without an additional compiler bug. Real-world V8 exploits at this maturity level typically require discovering a novel optimization pass bug that evades the deoptimization framework — something beyond what static analysis and black-box testing can reliably find.
